# LeviSW-MB v1.2

Репозиторий проекта контроллера матричного домофонного коммутатора **LeviSW-MB v1.2**: матрица `8 × 10` на 80 абонентов, MCU `ESP32-PICO-V3`.

Этот README — **главная инструкция проекта и точка входа для любой новой рабочей сессии ChatGPT/разработчика**. Перед началом работы обязательно прочитать этот файл, проверить актуальные ветки и состояние нужных файлов. Не полагаться только на историю чата.

---

## 1. Обязательные правила работы с репозиторием

1. **GitHub — основное хранилище всех существенных результатов работы.** Сохранять сюда проверенные схемные разборы, расчёты, таблицы, архитектурные решения, исходный код, тесты, инструкции и отчёты.
2. Перед изменениями определить тип работы и выбрать соответствующую ветку из раздела 2.
3. Перед редактированием прочитать текущие файлы и историю/состояние целевой ветки. Не перезаписывать существующие наработки вслепую.
4. Не смешивать аппаратную документацию, прошивку и экспериментальные тесты в одной случайной ветке.
5. Не переносить изменения между `main`, `master` и другими ветками автоматически. У `main` и `master` могут быть разные истории; сначала сравнить их.
6. Не коммитить предположения как подтверждённые факты. В документах явно разделять:
   - подтверждено схемой/даташитом;
   - подтверждено измерениями на реальной плате;
   - гипотеза или проектное предложение;
   - требует проверки.
7. Любое существенное изменение сохранять отдельным осмысленным коммитом с понятным сообщением на русском языке.
8. После записи проверить файл повторным чтением из GitHub и указать пользователю ветку, путь, ссылку и SHA коммита.
9. Не заявлять, что результат сохранён, пока GitHub не подтвердил успешную запись. Если нет доступа или операция не удалась — сообщить об этом прямо.
10. Не удалять и не заменять исходные файлы КД, даташиты, исходную адресную карту или существующую реализацию без отдельного обоснования и согласования.

| `docs/hardware-reference` | Основная ветка аппаратной документации | Анализ принципиальной схемы, трассировка сигналов, питание, защиты, распиновки, таблицы соединений, даташиты, PDF КД, результаты измерений и аппаратные отчёты |
| `feature/switchboard-controller` | Разработка полного контроллера/прошивки коммутатора | Исходный код прошивки, BSP, драйверы, конфигурация GPIO/SPI/I²C, логика матрицы 8×10, адресная карта 80 квартир, FSM, диагностика, сборка и программные тесты |
| `fix/safety-driver-audit` | Изолированные исправления и проверка безопасности драйверов | Аудит и исправления драйверов силовых/аналоговых микросхем, безопасные состояния при старте/сбросе, защита от ошибочной коммутации, тесты безопасности. Не использовать как общую ветку разработки |
| `i18n/russian-docs-comments` | Русификация документации и комментариев | Переводы документации и комментариев кода. Новые основные технические документы всё равно размещать в профильной ветке; при необходимости переносить русификацию согласованным PR |
| `master` | Существующая отдельная линия разработки/историческая база | Не использовать как целевую ветку по умолчанию. Сначала изучить её README, дерево, коммиты и отличия от `main`; не сливать с `main` без отдельного анализа |

**Правило выбора:** аппаратный вопрос — `docs/hardware-reference`; код контроллера — `feature/switchboard-controller`; исправление безопасности драйвера — `fix/safety-driver-audit`; русификация существующих материалов — `i18n/russian-docs-comments`; `main` — только главная инструкция и стабильная точка входа.

Ветка документации намеренно отдельная и **не объединена с `main`**. Не дублировать в `main` сами аппаратные документы: размещать там ссылки на них.

## 3. Структура и правила размещения файлов

### 3.1 Аппаратная документация — ветка `docs/hardware-reference`

Хранить материалы в `docs/hardware/`:

- `SCHEMATIC_ANALYSIS.md` — общий разбор листов принципиальной схемы;
- `SIGNAL_PATH_*.md` — подробные маршруты сигналов от входов до абонентских разъёмов;
- `POWER_*.md` — входное питание, DC/DC, шины питания, уставки и измерения;
- `PROTECTION_*.md` — защитные элементы, токи, напряжения, переходные процессы;
- `PINOUT_*.md` — распиновки разъёмов и микросхем;
- `MATRIX_8X10.md` — физическая и логическая матрица D0…D7 × E0…E9;
- `ELTIS_A5_HANDSET.md` — паспортные характеристики и аудит аналоговой трубки ELTIS A5, контакты Ln+/Ln−, разговорный тракт, вызов и открывание;
- `ELTIS_A3_ARCHIVE.md` — архивные сведения по A3; не использовать их как электрические данные A5;
- `MEASUREMENTS.md` — реальные измерения с условиями, приборами, точками подключения и результатами;
- `HARDWARE_ISSUES.md` — неподтверждённые вопросы, риски и план проверок.

Официальные PDF даташитов и КД размещать в `docs/datasheets/` и `docs/hardware/source/` соответственно, если это допускается лицензией и размером файла. В Markdown указывать производителя, номер документа, редакцию, дату и источник. Если PDF нельзя загрузить в GitHub из-за размера/ограничений, не имитировать загрузку: сохранить ссылку, контрольную сумму SHA-256, имя и инструкцию, где получить оригинал.

### 3.2 Прошивка и BSP — ветка `feature/switchboard-controller`

Сохранять в существующей структуре репозитория, не создавая параллельную структуру без необходимости:

- `bsp/levisw-mb-v1.2/` — аппаратный BSP, конфигурация платы, назначение GPIO и низкоуровневые интерфейсы;
- `examples/13_tps65261_dcdc/` и другие существующие примеры — сохранять их исходное назначение, не использовать как случайный контейнер всей прошивки;
- `examples/19_switchboard_controller/` — целевое приложение контроллера, если каталог ещё не занят другим содержимым;
- `components/` — отдельные повторно используемые драйверы/модули, если это соответствует принятой структуре ESP-IDF;
- `tests/` — автоматизированные и аппаратные тесты;
- `docs/software/` — архитектура ПО, FSM, API модулей, сборка, прошивка и диагностика.

Вынести в конфигурацию проекта все изменяемые аппаратные назначения: GPIO, SPI, I²C, CS/EN, адреса микросхем и соответствие каналов. Не зашивать физическую адресную карту квартир внутрь разрозненных драйверов.

### 3.3 Тесты и результаты

- Тест одного компонента — рядом с компонентом или в `tests/`, с инструкцией запуска.
- Тест матрицы — отдельный тест выбора D/E и проверки отсутствия одновременного включения несовместимых каналов.
- Логи UART, осциллограммы, фотографии стенда и таблицы измерений — в `docs/hardware/evidence/` либо `tests/results/` в зависимости от того, аппаратный это или программный результат.
- Для каждого результата записывать ревизию платы, питание, конфигурацию, приборы и условия измерения.

## 4. Технический контекст, который нельзя терять между чатами

- Проект: координатный аналоговый домофонный коммутатор LeviSW-MB v1.2.
- Контроллер: ESP32-PICO-V3.
- Адресная матрица: 8 × 10 = 80 абонентов; сохранять существующую физическую адресную карту квартир, не перенумеровывать без отдельного согласования.
- Штатное питание: 12 В.
- Текущая целевая абонентская трубка проекта: обычная аналоговая ELTIS A5 с двухпроводными клеммами Ln+/Ln−. Документы по A3 считать историческим архивом, пока пользователь отдельно не подтвердит смену целевой модели.
- ADG1608 — аналоговый мультиплексор; MC33879 и TLE94112EL — силовые драйверы, их нельзя считать взаимозаменяемыми или автоматически использовать как прозрачный речевой тракт.
- По имеющемуся анализу схемы +LINE проходит через защитный элемент VD6 на общий аналоговый вывод ADG1608, а выбранный канал идёт в одну из сетей AMP1…AMP8 и далее к XS3 / внешнему узлу LeviAMP. Это не прямое соединение с D0…D7: координаты D0…D7 выведены отдельно от MC33879 на XP2. Координаты E0…E9 идут от выходов TLE94112EL к XP3. Возможное функциональное сопряжение AMP→SW-OFS/MC33879→D требует pin-to-pin проверки RN24/RN25 и VD15…VD22. Прямое соединение -LINE с выходами E не подтверждено; на схеме отдельно показана цепь L3 || R23 между -LINE и GND.
- На листе питания +VIN через VD25 формирует промежуточную шину +Vdc, а +Vp создаётся отдельным DC/DC узлом. Не считать +Vp равным входным 12 В: измерить его и сверить с допустимым диапазоном ADG1608.
- Точная внутренняя схема ELTIS A5, электрические режимы на Ln+/Ln− и полный внешний кабельный маршрут должны быть подтверждены документом/фото/измерением. Паспорт подтверждает двухпроводный интерфейс, но не раскрывает полную электрическую модель. Не переносить схемы A3 на A5.

Эти сведения — исходный контекст, а не замена повторной проверке схемы, даташитов, платы и актуального кода.

## 5. Обязательный порядок начала работы в новом чате

Каждая новая сессия по проекту должна начинаться так:

1. Открыть этот `README.md` в `main` и прочитать его полностью.
2. Проверить список актуальных веток и определить целевую ветку по типу задачи.
3. Прочитать README и релевантные документы целевой ветки. Для аппаратной задачи обязательно начать с `docs/hardware/SCHEMATIC_ANALYSIS.md`, `docs/hardware/DATASHEETS.md` и соответствующей трассировки сигнала. Для программной — изучить BSP, примеры и текущую реализацию в `feature/switchboard-controller`.
4. Проверить, какие файлы уже существуют, последние коммиты и незавершённые задачи. Не создавать дубликаты документов и модулей.
5. Составить короткий план с указанием ветки и файлов, которые будут затронуты. Если пользователь поручил сразу выполнить работу, не задерживать процесс ненужными вопросами; уточнять только действительно недостающие критические данные.
6. Выполнить работу в профильной ветке, сохраняя существующие интерфейсы и обратную совместимость, где это возможно.
7. Проверить результат: для кода — сборка/тесты; для схемы — трассировка по листам и даташитам; для измерений — записать условия и значения.
8. Обновить связанные документы и список оставшихся вопросов.
9. Создать коммит с русским сообщением. При необходимости открыть Pull Request, но не сливать ветки без проверки.
10. Повторно прочитать изменённые файлы из GitHub и в итоговом сообщении указать: что сделано, ветку, пути, ссылки, SHA коммита, проверки и что осталось.

## 6. Формат итогового отчёта пользователю

После каждой существенной работы сообщать:

- **Статус:** выполнено / частично / не выполнено;
- **Ветка:** точное имя;
- **Изменённые файлы:** полный список путей;
- **Коммит:** сообщение и SHA;
- **Проверки:** что реально запускалось и какой результат получен;
- **Ограничения:** что не удалось подтвердить;
- **Следующий шаг:** конкретное продолжение работы.

Не писать «сохранено на GitHub», если нет подтверждённого успешного коммита.

## 8. Структура репозитория и быстрый старт

- `bsp/levisw-mb-v1.2/` — пакет поддержки платы (BSP) для ESP-IDF >= 5.2.
- `examples/` — примеры применения аппаратных узлов.

Подключение BSP в корневом `CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.16)
list(APPEND EXTRA_COMPONENT_DIRS "${CMAKE_CURRENT_LIST_DIR}/bsp/levisw-mb-v1.2")
include($ENV{IDF_PATH}/tools/cmake/project.cmake)
project(levisw_firmware)
```

Пример сборки существующего DC/DC-примера:

```bash
cd examples/13_tps65261_dcdc
idf.py set-target esp32
idf.py build
idf.py flash monitor
```

Перед использованием примера проверить его актуальность и конфигурацию целевой платы.
